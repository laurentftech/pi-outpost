## Why

Struck-through text reaches the model as ordinary text. In a `.docx` the parser reads no run
properties at all, so a run carrying `<w:strike/>` is indistinguishable from one that is not; in a
PDF the strike is not text at all — Word draws it as a thin filled rectangle over the glyphs, and
the text layer the extractor reads knows nothing about it.

That is not a formatting nicety. Crossing a sentence out is how a document says *this no longer
applies*, and both extractors currently hand the agent the crossed-out sentence as live content,
with nothing to mark it. A struck price, a withdrawn clause, a superseded instruction all read as
current. Confirmed on a real Word-authored PDF: the line "Copiez l'une des requêtes ci-dessous." is
struck through in the document and comes back from `extractPdf` as an ordinary numbered
instruction.

## What Changes

- `.docx` extraction reads run properties and renders a run carrying `<w:strike/>` or
  `<w:dstrike/>` as GFM `~~text~~`.
- `.docx` extraction renders `<w:b/>` as `**text**` and `<w:i/>` as `*text*`. These come with the
  strikethrough work rather than after it: reading `<w:rPr>` at all is the whole cost, and bold is
  how a document without heading styles marks its own structure.
- `<w:u/>` is deliberately **not** rendered. GFM has no underline, and treating an underlined
  paragraph as a heading would invent structure the document never declared.
- PDF extraction detects a drawn strikethrough from the page's drawing operations and renders the
  text under it as `~~text~~`. Underlines and horizontal rules, which are drawn with the same
  primitive, are not mistaken for one.
- Existing tracked-change behaviour is unchanged: `<w:del>` text stays dropped entirely. A tracked
  deletion is not the same statement as a manual strikethrough — the first is a revision the author
  has already made, the second is content the author left in place, crossed out.

Not breaking. A document with no struck, bold or italic run extracts exactly as it does today.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `docx-documents`: extraction gains run-level formatting — strikethrough, bold and italic are
  carried into the markdown instead of being flattened away.
- `pdf-documents`: extraction gains strikethrough detection from the page's drawing operations,
  and states the limits of what that detection claims.

## Impact

- `server/src/docx.ts` — `parseBody` gains an `<w:rPr>` reader and emits marker-wrapped text. The
  block model (`DocxBlock`) and `renderBlock` are unaffected: markers travel inside the existing
  `text` strings.
- `server/src/pdf.ts` — a new reader over `page.getOperatorList()` alongside the existing
  `getTextContent()` call, CTM tracking for the drawn paths, and a strike/underline discriminator.
  `TextPiece` gains a struck flag; `buildLines`, `lineCells` and `renderPage` carry it through.
- `server/src/markdownTable.ts` — unchanged. `escapeCell` escapes backslashes and pipes and collapses
  whitespace; it does not touch `~` or `*`, so the markers survive a table cell as they are.
- Tests: `server/test/docx.test.ts`, `server/test/pdf.test.ts`, and new fixtures generated by the
  existing `server/test/fixtures/make-docx.mjs` and `make-pdfs.mjs`.
- Out of scope, same class of gap, left for a separate change: `server/src/pptx.ts` (`<a:rPr
  strike="sngStrike">`) and spreadsheet cell formatting. Also out of scope: strikethrough applied
  through a character *style* rather than direct run formatting, which would need `styles.xml`
  resolution.
- No protocol, UI, or configuration change. The tool signatures do not change.
