### Bug found by task 4.2 and fixed here: `--open-in` never reached configuration

`parseCli` parsed and validated `--open-in` but returned it as a top-level field of `ParsedCli`, a sibling of `flags`. `index.ts` starts the server with `loadConfig(LAUNCH_DIR, cli.flags)`, and `applyRuntime` reads `flags.openIn` — which was always `undefined`. So `--open-in browser` did nothing; `--open-in window` only "worked" because `window` is already the default. This broke the `TheOperatorCanAskForATab` scenario and the requirement's "overridable from the command line" at the real boundary. Every unit passed: `cli.test.ts` asserted the top-level field, `config.test.ts` hand-built a `{ openIn }` flags object — nobody threaded `parseCli` → `loadConfig`.

- Fix: `parseCli` now puts `openIn` inside the `flags` object (`CliOptions.openIn` already existed for it), removed from the top-level `ParsedCli`. `server/src/cli.ts`.
- Tests: `cli.test.ts` assertions moved to `.flags.openIn`; new `config.test.ts` seam test drives `argv → parseCli → loadConfig` and asserts `config.openIn === "browser"`, so the regression cannot come back through the gap the old tests left.
