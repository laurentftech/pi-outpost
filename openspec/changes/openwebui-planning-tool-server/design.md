# Design

## Context

- The version 3 timeline lives entirely in `shared/`:
  - parsing and limits: `parseSerializedStructuredExchange`, `structuredExchangeBounds`;
  - the schema check: `checkStructuredExchangeSchema`;
  - the timeline rules: `timelineIssues`;
  - the comparison: `compareTimelines`, `withoutComparison`.

  pi-outpost's `timelineComparisonTool.ts` already drives these from a pi tool. The new server drives
  them from HTTP instead.
- `ui/src/presentations/TimelineView.tsx` is a React component. Its only imports are React and
  `shared/` (plus `figureDrawing`). It holds scales, enlarge and item details, and needs no
  application context, so it can be bundled alone.
- `ui/src/export/conversationHtml.ts` builds static, script-free HTML for archives. It is not
  reusable here: the embed must run scripts to be interactive.
- Open WebUI calls a global tool server **from its backend**. With
  `ENABLE_FORWARD_USER_INFO_HEADERS` it forwards the user (`X-OpenWebUI-User-Id`, …) and the chat and
  message ids.
  - A tool answer with `Content-Disposition: inline` and `text/html` becomes an iframe embed.
  - The iframe sandbox allows scripts, but not same-origin by default.
  - The embed talks to the chat through `postMessage`: `iframe:height`, `input:prompt`,
    `input:prompt:submit`.
- The server stack is already Fastify in `server/`.

## Goals / Non-Goals

**Goals:**
- One timeline contract: the same verdicts and the same documents in pi-outpost and in Open WebUI.
- Edits that weak models get right: identifiers and small operations, never a retyped document.
- A server the IT department can host with nothing but Node, a directory and a secret.

**Non-Goals:**
- Team sharing, groups, permissions beyond "owner".
- Other structured-exchange kinds (tables, figures, profiles). The server is built so they could be
  added, but this change ships timelines only.
- Publishing the package to npm, or a container image. These wait for the hosting decision.
- docx/pptx export of a planning.

## Decisions

### A separate workspace package, `openwebui/`

- **Choice:** a new package (`@pi-outpost/openwebui`, private) beside `server/`, depending on
  `@pi-outpost/shared`, with no dependency on `server/` or on pi.
- **Rationale:** pi-outpost's server carries pi, sandboxes and a WebSocket protocol, none of which
  apply here. Keeping the dependency one-way (on `shared/` only) keeps the contract single without
  pulling the agent along.
- **Alternative rejected:** a route inside `server/`. It would make every Open WebUI deployment run
  the whole pi-outpost server.

### Plain OpenAPI over Fastify, not MCP

- **Choice:** Fastify routes with JSON schemas. The OpenAPI document is generated from those
  schemas.
- **Rationale:** Open WebUI documents rich UI embeds for OpenAPI tool servers. Its docs say nothing
  about embeds from MCP servers, and the embed is the point.
- **Revisit when:** Open WebUI documents MCP embeds, or MCP Apps.

### Trust: bearer secret first, identity second, signed when possible

- **Bearer check:** a Fastify `onRequest` hook compares the bearer token, the tool server
  connection's key, in constant time before any route runs. The server listens on a configured
  address, `127.0.0.1` by default.
- **Identity, two modes, chosen by configuration** (observed on v0.11.4, see `prototype.md`):
  - **Signed (recommended).** Open WebUI has `FORWARD_USER_INFO_HEADER_JWT_SECRET` set. It sends
    `X-OpenWebUI-User-Jwt`, an HS256 token with `sub` (user id), `iss: "open-webui"` and a 300 s
    `exp`, *instead of* the plain headers. The server verifies the signature, `iss` and `exp`, and
    the owner is `sub`. A missing, forged or expired token is refused.
  - **Plain.** The owner is `X-OpenWebUI-User-Id`, refused if absent. It is trusted only because the
    bearer secret proves the caller is Open WebUI.
  - In signed mode, plain headers are ignored, so a request cannot pick its owner.
- **Rationale:**
  - Plain headers are claims, which only the bearer secret vouches for.
  - The signed token binds the identity to a key Open WebUI alone holds, and expires, so a leaked
    request log cannot be replayed for long.
  - The bearer stays mandatory in both modes. It is what Open WebUI's connection settings carry.
- **Without forwarding:** if `ENABLE_FORWARD_USER_INFO_HEADERS` is off, no identity arrives, and
  every planning request is refused, by design.

### Storage: one directory per owner, one file per revision

- **Layout:** `<root>/<owner-hash>/<planning-id>/<revision>.json`, plus a small `meta.json` (title,
  current revision, timestamps).
  - The owner directory is a hash of the user id, so an id never becomes a path.
  - Planning ids are random, generated by the server.
- **Writes:** to a temporary file, then renamed. A per-planning lock serialises updates. The
  revision check (`base_revision`) makes concurrent writers fail loudly, not overwrite.
- **Rationale:** files give the IT department nothing to run, can be backed up as they are, and each
  revision is a document pi-outpost opens directly.
- **Alternative:** SQLite. Deferred until sharing or search needs queries.

### Targeted operations

- **Operations:** `set_title`, `set_time`, `add_task`, `change_task`, `move_task` (before/after an
  id, or to an index), `remove_task`, `add_item`, `change_item`, `remove_item`, `add_separator`,
  `remove_separator`, `add_dependency`, `remove_dependency`, `set_periods`, `set_references`
  (these two replace the whole list, which is short by nature).
- **Addressing:** by identifier. Items need an `id` to be changed or removed. Creation may assign
  missing item ids (`<task>.<n>`), and the answer returns them.
- **Separators:** they have no ids in the contract, so they are addressed by position, the row index
  shown by `get_planning`.
- **Application:** operations apply to a copy, in order. The first failure aborts with its index.
  Then the whole result goes through the same validation as a creation.
- **Rationale:** a weak model edits a date by naming it. It never re-emits 300 lines, so it never
  drifts on the 299 it did not mean to touch. JSON Patch was considered and rejected: its array
  indices go stale between a read and a write, and models get them wrong.

### The embed: one HTML file, viewer inlined

- **Build:** a Vite library build of a small entry that mounts `TimelineView`, produces one script.
- **Answer:** `show_planning` returns HTML that carries the planning (and the comparison, if asked)
  as JSON, plus the viewer, inlined.
- **Why inline only** (settled by the prototype, see `prototype.md`; Open WebUI v0.11.4):
  - Inline embeds rendered at 400 kB and survived reloading and reopening the chat.
  - They need nothing from the user's network: the browser never contacts the tool server, so the
    server can stay reachable from Open WebUI's backend only.
  - **Rejected, `shell`:** a `<script src>` to the server. It works only where the browser reaches
    the server.
  - **Rejected, `Location` embeds:** the iframe's `src` points at the server. It also needs the
    browser to reach the server, and an unauthenticated page URL that would have to be a lasting
    read capability stored in the chat.

  Either can come back as a later option if chat storage becomes a concern.
- **Sandbox-friendly:**
  - no storage;
  - no same-origin assumptions;
  - the planning travels in the HTML, never through `window.args`, which Open WebUI cannot set
    without same-origin;
  - height reported with a `ResizeObserver` on the viewer's own content element → `iframe:height`.
    The document's `scrollHeight` never drops below the frame's default 150 px.
- **Clicks:** `onSelect` sends `input:prompt` with a sentence naming the item and the planning. It
  never sends `input:prompt:submit`. Observed: the input fills and nothing is sent.
- **The model never sees the show answer.** For an external tool, Open WebUI replaces an inline
  HTML answer with a fixed "Embedded UI result is active" message. So `show_planning` carries no
  summary for the model. The model reads a planning through `get_planning`, and the `show_planning`
  description says so.

### Tool descriptions carry full examples

- **Content:** a complete minimal timeline in `create_planning` and a complete update in
  `update_planning`.
- **Tests:** they parse the descriptions and run the examples (spec scenarios
  `TheCreationExampleIsValid` and `TheUpdateExampleApplies`), so the examples cannot rot.
- **Rationale:** weak models read the tool description and nothing else.

## Risks / Trade-offs

- **Embed persistence**: no longer a risk. It was observed to persist on v0.11.4. A later Open
  WebUI could change it; `show_planning` is cheap to call again.
- **Inline embeds grow chat storage.** Every show stores the viewer, a few hundred kB. Mitigation, if
  it bites: a `Location` mode, at the cost of browser reachability (see the embed decision).
- **Forwarded identity depends on Open WebUI configuration.** If `ENABLE_FORWARD_USER_INFO_HEADERS`
  is off, every request is refused, by design. The deployment doc says so first.
- **The revision ceiling refuses updates** instead of pruning. That is safe, but annoying.
  Revisit with real usage: pruning everything but the first and last N.
- **Open WebUI moves fast.** Header names and embed behaviour are pinned in the deployment doc, with
  the Open WebUI version they were checked against.

## Migration Plan

New package and nothing existing changes, so no migration. Rollback is removing the tool server
from Open WebUI's admin settings. The stored plannings stay as plain JSON files.

## Open Questions

- Hosting: next to Open WebUI on the IT department's side, or elsewhere. Configuration covers both.
  The deployment doc will name the IT department's choice once made.
- ~~Embed persistence and browser reachability~~: settled by the prototype (`prototype.md`). Inline
  only, and nothing asks the browser to reach the server.
