# Scenario coverage — add-structured-exchange-profile-rules

Every scenario the four deltas declare, and the assertion that would fail if its contract broke. A
scenario is `covered` only when a test's *assertions* check the WHEN/THEN at the boundary the scenario
describes.

Five boundaries carry this change, and each scenario is cited at the one it names. The rules format,
the evaluation and the report are pure code in `shared`, tested under Node on the smallest rules file or
document that breaks each rule, asserting rule and pointer. The project's files are tested on real
directories: a missing, escaping or edited rules file, read again with nothing restarted. The agent's
tools are driven as the agent calls them, asserting the text it reads back, whether anything reached
the interface's channel, and whether a file exists afterwards. The reader's statement and export
controls are rendered in jsdom. The reference validator is the shipped bundle, rebuilt and copied to a
directory with no path back to the repository, executed with only `PATH` in its environment.

Mutations confirmed the new checks bite: a neighbour lacking an attribute read as a failure instead of
unknown, a refuse rule reported instead of refused, and a report finding counted twice across two rows
each failed the suite. `ALargeBatchRunsInOneProcess` records its duration as a test diagnostic: ten
thousand requirements in 2.7–2.9 s on the development machine (Intel iMac), in one invocation.

Scenarios carried unchanged into a MODIFIED requirement keep the evidence of the change that introduced
them, re-read against the tests as they stand now.
