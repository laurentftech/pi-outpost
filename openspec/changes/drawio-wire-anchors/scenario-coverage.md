Calibration (task 1.2, `scripts/probes/drawio-anchor-calibration.mts`):
- The two jgraph examples, drawn by people, report nothing.
- Codestral: the rules alone find one shared point (two unlabelled wires on the top of "Batterie"), eight ends facing away and one detour (170 units between facing sides 30 apart). All five wires also run through their own ends, so `drawio_check` reports those five with the existing own-ends message and adds only the shared point. One message per wire about its ends.
- Gemini 3.5 Flash and GPT-5.6 Luna: one shared point each on "inverter", an outgoing and an incoming flow on one point. In Luna's file the two wires overlap along the same line.
- Every one of these is a defect a reader would see. 2× and 80 units stay.

Live run (task 4.2, `scripts/probes/drawio-anchors-live.mjs`, one turn per model):
- GPT-5.6 Luna drew the flow diagram clean on its first write: each flow on its own point, the sides facing each other. The check had nothing to report.
- Codestral loaded `drawio_check` through `tool_search` and got five warnings: three wires through their own ends, four flows on one point of the controller, two on one point of the actuator. It understood them and tried to change `exitX/entryX`. Every `edit` was refused with "Each oldText must be unique", because two wires had the same style string, and it looped on the same report until the probe was stopped at 101 s. The rewrite was never applied, so the run shows the warnings reaching the agent and being acted on, not the corrected file.
- The run exposed a wrong message: four flows on one point with two free positions were told "no free point left". The free points are now handed to the first wires and only the rest are sent to another side ("Codestral's four flows on one point …" in `drawioWires.test.ts`).
- A second Codestral run, after that fix, showed the messages contradicting each other. Two flows through their own ends were both sent to `exitX=1;exitY=0.5`, which would share a point again, while the shared-point message proposed points on the side they were told to leave; Codestral followed the latter. Its edits were refused again ("Found 5 occurrences … must be unique") and it looped. The ends that must move now get their points from one placement shared by every message (design.md, "One placement for the ends that must move"). "Codestral's flows through their own ends: …" in `drawioWires.test.ts` asserts distinct facing points (0.25 and 0.75), no shared-point message about them, and no warning once the advice is followed. The test fails with the previous code.
- A third Codestral run, after the report started saying to include a connector's `id="…"` in the text an `edit` replaces, finished in 22 s. Its first check reported four labels on shapes and four wires through their own ends, with distinct facing points: 0.25 and 0.75 for the two wires between the controller and the actuator. It made one `edit` keyed on `<mxCell id="6" …`, applied exactly the proposed values, and the next check reported no defect. All four wires were still routed by the check, with no wire passing silently as unrouted. Its diagram left out the "alarmes" flow it had been asked for; that is the model's content, not something the check can see.
- A batch of four further diagrams with Codestral (`scripts/probes/drawio-anchors-batch.sh`): every anchor warning it raised was a real defect, with no false positive. It showed three things on pi-outpost's side, all fixed in group 5. A check run beside an edit reported "no defect" on a file the edit was rewriting. A label written as a child cell with an absolute geometry was not read as the wire's label. The report gave no order, so a model could keep moving a label while the wire under it stayed wrong. What the model did otherwise (no check at all, stopping with errors left) is its own quality and not judged here.
- Rerun of the same four prompts with Codestral (`scripts/probes/drawio-anchors-audit.mjs` on the logs): every multi-warning report carried the order line. One run showed checks answering while an edit sent with them was still running, and a last report of 0 issues on a file with 3. The temporary directory is under /var, a link to /private/var, and the write registry compared the two spellings as different files. It now resolves links, and the wire test runs on the unresolved path, which fails without the fix.
- GPT-5.6 Luna, the same four prompts, in the user's own run: every diagram passed `drawio_check`, yet the wires carried hooks and jogs a few units long, drawn as pin heads. They came from waypoints a few units off their neighbours, which the check did not look at. The needless-bend rule now reports them: nine on three diagrams, none on the fourth. Each fix was tried on the route first, and following them converges without losing the detours the waypoints make around shapes.
- GPT-5.6 Luna, rerun with the needless-bend rule (`luna2-*`): every diagram passed the check, yet steps of 5 to 15 units showed in the screenshots. They came from fixed ends at the same fraction of boxes of different heights, with no waypoint. The rule now covers fixed ends too, under twenty units. Its fixes are tried on the route before they are given: two-decimal values left one-unit steps, and a level value on a rhombus did not level anything. Following them clears every step, as the before and after screenshots show.
